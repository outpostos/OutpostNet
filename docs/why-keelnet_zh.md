# 为何选择 Keelnet？

## "这不就是个更复杂的 frp 吗？"

如果您有这个疑问，那么恭喜，您问到了点子上。

从表面上看，用 Keelnet 完成一次简单的端口转发，确实比 `frp` 复杂得多：
- **`frp`**: 2 个进程，2 个配置文件。
- **Keelnet**: 3 个进程，3 个配置文件，还需要理解 `Service`, `Workload`, `Endpoint` 等一系列云原生概念。

**如果您的目标只是将一个内网端口暴露到公网，那么 `frp` 可能是更直接的选择。**

**但如果您的目标远不止于此，Keelnet 的设计将为您揭示一个全新的可能性。**

---

## Keelnet 的初心：为极端环境的韧性而生

Keelnet 的核心设计目标 **并非** 替代 `frp`，而是构建一套 **专为极端环境设计的边缘计算网络平台**。

想象以下场景：
- **战术前线**: 网络连接极不稳定，IP 地址频繁变动，与指挥中心的连接可能随时中断数小时甚至数天。
- **灾后救援**: 基础设施被毁，依赖临时的、不可靠的网络（如卫星、无人机中继）进行通信。
- **远洋货轮/勘探平台**: 与陆地数据中心的连接是高延迟、低带宽且昂贵的。

在这些场景下，传统的云原生技术栈（如标准的 Kubernetes + Istio）面临着前所未有的挑战：
- **强依赖中心节点**: `apiserver` 或 `istiod` 一旦失联，边缘节点可能陷入功能瘫痪。
- **网络敏感性**: 对稳定的 IP 地址和低延迟网络有较强依赖。
- **资源消耗过高**: 在资源受限的边缘设备上运行完整的服务网格组件过于沉重。

**Keelnet 正是为了在这些“云原生技术真空区”，提供高韧性的服务发现、路由和管理能力而设计的。**

---

## 重新理解 Keelnet 的架构

为了实现上述目标，Keelnet 采用了一套与传统代理截然不同的架构。让我们来澄清一些常见的误解。

### 误解 1：`OutpostNet-server` 是一个中心化的代理服务器

**这是对 Keelnet 架构最大的误解。**

- **`frp` 的 server (`frps`)**: 是一个中心化的流量中转站，所有代理流量都必须经过它。
- **Keelnet 的 server (`OutpostNet-server`)**: 是一个 **分布在每个边缘节点上的代理/守护进程 (Agent/Daemon)**。它的角色更像 `kubelet` 或 `istio-proxy`，是 Keelnet 在每个节点上的“本地代表”。

正确的部署架构应该是这样的：

```
+------------------ 节点 1 ------------------+      +------------------ 节点 2 ------------------+
|                                            |      |                                            |
|  +--------+      +----------------------+  |      |  +--------+      +----------------------+  |
|  |  应用  |      |                      |  |      |  |  应用  |      |                      |  |
|  +--------+      |   OutpostNet-server-1   |  |      |  +--------+      |   OutpostNet-server-2   |  |
|  | Sidecar| ===> | (节点代理)           |  |      |  | Sidecar| ===> | (节点代理)           |  |
|  | Client |(unix)|                      | ======>|  | Client |(unix)|                      |  |
|  +--------+      +----------------------+  (gossip) +--------+      +----------------------+  |
|                                            |      |                                            |
+--------------------------------------------+      +--------------------------------------------+
```

### 误解 2：`client` 和 `server` 的职责混乱

在理解了 `server-per-node` (每节点一个 Server) 的架构后，`client` 的角色就清晰了：

- **`OutpostNet-client`**: 作为 Sidecar 部署在应用一侧，它代表了应用的“网络身份”。
- **`OutpostNet-server`**: 作为节点守护进程，它代表了节点的“网络身份”。

`client` 通过高效的 Unix Socket 与本地 `server` 通信，而 `server` 之间通过 `gossip` 协议交换信息，共同构建出一个高韧性的服务网格。

### 误解 3：`Service/Workload/Endpoint` 等概念过于复杂

这套抽象恰恰是实现 **离线自治** 和 **动态服务发现** 的基石。

- **场景：节点 IP 地址变化**
  - **`frp` 会怎样?**: 连接中断，需要手动修改配置。
  - **Keelnet 会怎样?**: `server` 的 IP 变了，但应用 `client` 与本地 `server` 的通信 (Unix Socket) 不受影响。对端的 `server` 通过 `gossip` 协议最终会发现新地址，网络会自动恢复。服务本身是稳定的，对应用透明。

- **场景：与中心控制面失联**
  - **传统云原生会怎样?**: 无法进行新的服务部署和策略变更。
  - **Keelnet 会怎样?**: 每个 `server` 都缓存了配置和 PKI 凭证。即使失联，节点内部和已知的节点之间依然可以基于缓存的策略进行安全通信，实现“离线自治”。

## "Express Mode" 的真正意义

既然 Keelnet 的架构如此强大，为什么还要提供一个简化的 `Express Mode` 呢？

> “一个复杂的系统，若能以简单的方式呈现，这便是架构的魅力所在。”

`Express Mode` **不是对架构的妥协，而是对开发者体验的尊重**。它的目标是：

1.  **隐藏复杂性**: 为简单场景（如本地开发、单节点部署）提供一个直观的接口，让用户无需理解完整的分布式架构也能快速上手。
2.  **提供渐进式学习路径**: 用户可以从 `Express Mode` 开始，当需求变得复杂时，可以平滑地迁移到功能更完整的“标准模式”，底层的核心能力一脉相承。
3.  **加速开发与测试**: 让开发者能用一条命令就在本地模拟出一个简单的节点环境，极大地提升了开发和调试效率。

它不是为了让 Keelnet “变成”`frp`，而是为了让 Keelnet 在需要简单时，**用起来能像 `frp` 一样简单**。

---

## 结论：何时选择 Keelnet？

选择 Keelnet，当您需要：

- **高韧性与高可用性**: 在网络不可靠的边缘环境中，保证服务的持续运行。
- **离线自治能力**: 在与控制中心失联时，系统依然能够自主工作。
- **动态服务发现**: 自动适应边缘环境中频繁变化的网络拓扑和 IP 地址。
- **零信任安全模型**: 基于 PKI 体系，实现端到端的加密和细粒度访问控制。
- **一个面向未来的平台**: 一个能够从简单的节点代理，平滑演进到复杂的多集群分布式服务网格的平台。

Keelnet 的设计蕴含着在极端条件下对系统生存能力的深刻思考。它的“复杂”，恰恰是其在严酷环境中保持“韧性”的根源。
