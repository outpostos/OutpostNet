# OutpostNet 当前实现状态

## 📍 当前阶段：Phase 1 - 节点服务网格

### 🎯 当前实现概述

OutpostNet 目前实现了一个**功能完整的服务网格代理系统**，采用 **服务器中转架构模式**，在单个边缘节点内提供完整的服务网格能力：

```
                    OutpostNet 当前实现架构 (服务器中转模式)
    ┌─────────────────────────────────────────────────────────────┐
    │                  OutpostNet-server (端口17000)                │
    │              ┌─────────────────────┐                        │
    │              │   服务注册中心       │                        │
    │              │  - K8s Memory       │                        │
    │              │  - 负载均衡器        │                        │
    │              │  - 工作连接池管理    │                        │
    │              │  - 数据中转服务      │                        │
    │              └─────────────────────┘                        │
    │                        │                                    │
    │           ┌─────────────┼─────────────┐                     │
    │           │             │             │                     │
    │  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐            │
    │  │Register Client│ │Register Client│ │Proxy Client │        │
    │  │控制连接+工作池│ │控制连接+工作池│ │控制连接+代理│         │
    │  │             │ │             │ │             │           │
    │  │后端服务A     │ │后端服务B     │ │前端应用     │           │
    │  └─────────────┘ └─────────────┘ └─────────────┘            │
    └─────────────────────────────────────────────────────────────┘

    数据流向: 前端应用 → Proxy Client → Server → Work Connection → Register Client → 后端服务
```

### 🔧 核心功能已实现

#### ✅ 服务注册与发现
- **K8s兼容的服务注册**: 使用 `registry.NewK8sMemoryRegistry()` 内存注册表
- **动态服务发现**: 客户端通过 `QueryService` 消息查询可用服务
- **标签选择器**: 支持基于labels的服务筛选

#### ✅ 负载均衡与健康检查
- **多种负载均衡算法**: round_robin, weighted, least_conn
- **健康检查机制**: 自动检测和移除不健康的服务实例
- **故障转移**: 自动将流量从故障实例转移到健康实例

#### ✅ 服务器中转架构代理支持
- **控制连接分离**: JSON消息控制平面与原始数据分离
- **工作连接池**: 预建立连接池，支持高并发数据转发
- **服务器中转**: 所有数据通过服务器中转，确保正确的服务网格架构
- **TCP数据桥接**: 使用io.Copy进行高效双向数据转发

#### ✅ Express Mode用户体验
- **一行命令启动**: 极简的命令行界面
- **配置自动生成**: 自动生成K8s兼容的YAML配置
- **快速演示脚本**: 5分钟完整功能验证

### 🚧 当前架构的局限性

#### 1. **中心化架构限制**
- 所有客户端都依赖中心的 OutpostNet-server
- 服务器故障会导致整个网格不可用
- 数据必须通过服务器中转（服务器中转架构特性）

#### 2. **单点性能瓶颈**
- 所有数据转发都经过中心服务器（正确的服务网格架构）
- 服务器需要处理所有连接的数据中转
- 单个服务器的处理能力限制了整体性能

#### 3. **网络依赖**
- 需要所有节点都能连接到中心服务器
- 不支持离线运行或边缘自治
- 无法处理网络分区或间歇性连接

> **注意**: 当前的中心化数据转发是正确的服务网格架构设计，确保了数据流向的可控性和安全性

### 为什么选择分阶段实现？

#### 1. **风险控制**
- 分布式系统极其复杂，一次性实现风险巨大
- 分阶段可以在每个阶段验证关键假设
- 降低技术债务和重构成本

#### 2. **用户反馈驱动**
- Phase 1提供可用的MVP，收集真实用户反馈
- 基于实际使用场景调整Phase 2/3的设计
- 避免过度设计不需要的功能

#### 3. **技术成熟度**
- 中心化架构技术成熟，实现风险低
- 为团队积累分布式系统开发经验
- 建立完整的测试和部署流程

#### 4. **兼容性保证**
- 每个阶段都保持向前兼容
- 用户可以平滑升级，无需重新配置
- 降低采用门槛和迁移成本

## 🛠️ 服务器中转架构技术实现

### 核心架构组件

#### 1. **WorkConnManager (工作连接池管理器)**
```go
// WorkConnManager 管理工作连接 (服务器中转模式)
type WorkConnManager struct {
    clientPools map[string]*ClientWorkConnPool
    mu          sync.RWMutex
}

// ClientWorkConnPool 单个客户端的工作连接池
type ClientWorkConnPool struct {
    ClientID    string
    workConnCh  chan net.Conn
    poolCount   int
    mu          sync.RWMutex
}
```

#### 2. **消息协议 (服务器中转模式)**
```go
// 控制连接消息类型
MsgTypeReqWorkConn      MessageType = "req_work_conn"         // Server 请求 Register Client 创建工作连接
MsgTypeNewWorkConn      MessageType = "new_work_conn"        // Register Client 创建新工作连接
MsgTypeStartWorkConn    MessageType = "start_work_conn"      // Server 指示工作连接开始处理特定隧道
```

#### 3. **数据桥接机制**
```go
// forwardTCPData 进行TCP数据转发 (kube-frp模式)
func (c *Client) forwardTCPData(localConn, workConn net.Conn, proxyName string) {
    // 使用io.Copy进行双向数据转发 (kube-frp模式)
    done := make(chan struct{}, 2)
    
    // local client -> work connection
    go func() {
        defer func() { done <- struct{}{} }()
        _, err := io.Copy(workConn, localConn)
    }()
    
    // work connection -> local client
    go func() {
        defer func() { done <- struct{}{} }()
        _, err := io.Copy(localConn, workConn)
    }()
    
    <-done
}
```

